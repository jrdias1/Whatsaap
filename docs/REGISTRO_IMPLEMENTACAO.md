## Correção do provisionamento Superadmin — 19/10/2026

- **Causa comprovada:** o fixture Playwright criava o código `PLATFORM-BROWSER-${suffix}` usando `randomBytes(...).toString('hex')`, cujo sufixo contém letras `a`–`f` em minúsculas. `PlatformService.provision()` normaliza o valor recebido com `toUpperCase()` e consultava `Plan.code` por igualdade exata. A comparação no PostgreSQL é sensível a maiúsculas/minúsculas: códigos com letras no sufixo não coincidiam; sufixos compostos apenas por dígitos passavam, explicando os resultados alternados. A listagem administrativa também lê `Plan`, porém apenas lista planos habilitados; ela não garantia que a busca exata do provisionamento encontraria a linha de caixa diferente. Fixture e API usam o banco indicado pela configuração local do Playwright/API, `clinic_browser_validation`; a confirmação do plano ocorre antes de provisionar, sem transação não confirmada ou cleanup intermediário.
- **Correção mínima:** `platform.service.ts` mantém a consulta exata pelo código normalizado como caminho primário e, se não houver correspondência, procura código equivalente sem distinção de caixa; código desativado continua rejeitado. O mesmo contrato de lookup foi aplicado à troca de plano. Fixture Playwright passou a persistir o código canônico em maiúsculas. Não houve mudança de schema/migration, permissões, MFA, chave idempotente ou catálogo/preço dos planos.
- **Regressão API:** `platform-onboarding.db.e2e-spec.ts` persiste deterministicamente o plano em minúsculas, envia o código em maiúsculas, verifica 400 para plano inexistente e desativado, 201 para plano válido, repetição idempotente sem duplicar tenant/unidade/assinatura/convite. Resultado focado: **2/2 aprovados** (1 arquivo).
- **Build:** build completo da API aprovado após a correção. Build Web aprovado anteriormente e não precisou ser repetido porque não houve alteração no Web além da asserção Playwright.
- **Playwright focado:** `platform-admin.spec.ts`: **1/1 aprovado** na execução final.
